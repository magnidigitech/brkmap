# 3. Google API Key Architecture

I would use **two keys**, not one.

### Key 1 — Browser

```text
NEXT_PUBLIC_GOOGLE_MAPS_BROWSER_KEY
```

Used by:

* Maps JavaScript API
* Browser map UI
* Places autocomplete if implemented client-side

Restriction:

```text
Application:
Websites

Allowed:
https://yourdomain.com/*
https://www.yourdomain.com/*
```

API restrictions:

```text
Maps JavaScript API
Places API (New)
```

Google recommends application and API restrictions to prevent unauthorized usage and billing abuse. ([Google for Developers][1])

### Key 2 — Server

```text
GOOGLE_MAPS_SERVER_KEY
```

Used ONLY by:

* Routes API
* Geocoding API
* Places Web Service when needed

Never expose this key to the browser.

Restrict it to your VPS/server IP and only the required APIs. Google explicitly recommends IP restrictions for server-side web services. ([Google for Developers][1])

# 20. Google Routes API usage

For two locations:

```text
A → B
```

use **Compute Routes**.

For many locations:

```text
A
B
C
D
E
F
```

use **Compute Route Matrix**.

The matrix gives your application the travel-time/distance relationship needed by the optimizer.

That's much better than requesting individual routes repeatedly.

# 21. Don't ask Google to "optimize the political schedule"

This is an important architectural decision.

Google should answer:

> "How long does it take to travel from A to B?"

Your system should answer:

> "Should the candidate go from A to B next?"

Your optimizer owns the second question.

# 22. Smart Scheduling Algorithm

I'd implement a **two-stage optimizer**.

## Stage 1 — Constraint construction

Classify every event:

```text
FIXED
FLEXIBLE
OPTIONAL
```

Example:

```text
Collector Meeting
10:30
FIXED

Village A
09:00–12:00
FLEXIBLE

Village B
09:00–13:00
FLEXIBLE

Party Office
08:30
FLEXIBLE
```

---

# 23. Hard Constraints

These cannot be violated.

```text
1. Fixed event time
2. Event duration
3. Candidate cannot attend two places simultaneously
4. Travel time must fit
5. Working-day start
6. Working-day end
```

For example:

```text
A ends at 10:00

Travel A → B = 35 minutes

B cannot start before 10:35
```

---

# 24. Soft Constraints

These can be violated if necessary.

```text
Preferred time
Priority
Minimal travel
Minimal waiting
Preferred geographical grouping
```

---

# 25. Objective Function

A practical score:

```text
TOTAL COST =

Travel Time × 1.0

+ Waiting Time × 0.5

+ Late Arrival × 100

+ Fixed Event Violation × 1000

+ Low Priority Miss × 20

- Event Priority Bonus
```

The exact weights should be configurable.

This can dramatically improve political campaign schedules.

Suppose you have:


Instead:


You can cluster locations using geographic distance first, then optimize the sequence inside each cluster.

One particularly important implementation detail: **do not put the Google server API key in Next.js client code**. Keep Routes/Geocoding server-side, while the browser-facing Maps key is separately restricted. Google's current security guidance explicitly recommends separate keys and appropriate application/API restrictions. ([Google for Developers][1])

For the actual V1, I would use **Next.js + PostgreSQL + Prisma + Redis + Google Maps Platform + OR-Tools**, with a `RoutingProvider` abstraction so Google can later be replaced by OSRM/Valhalla without changing the scheduling engine.
